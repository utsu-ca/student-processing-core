KEY ARCHITECTURAL PATTERNS:

1. DATABASE PER SERVICE
   • Each service owns its data
   • No shared database (prevents tight coupling)
   • AuthSvc: auth_db (users, roles, permissions, audit log)
   • MailSvc: mail_db (email queue, status, delivery tracking)

2. SERVICE DISCOVERY
   • Local: Docker DNS (authsvc:8080)
   • Kubernetes: ClusterIP DNS (authsvc.default.svc.cluster.local)
   • Azure: DAPR sidecars (localhost:3500)
   • GCP Cloud Run: IAM service accounts + hardcoded URLs

3. AUTHENTICATION BETWEEN SERVICES
   • Service Tokens: Long-lived symmetric key (32+ chars)
   • Transport: Authorization header with service token
   • Verification: HMAC constant-time comparison
   • Separate from user JWT tokens

4. FAILURE HANDLING
   • Retry logic with exponential backoff
   • Circuit breakers (prevent cascading failures)
   • Timeouts on all inter-service calls
   • Fallback responses when services unavailable
   • Health checks (/health endpoints)

5. SCALING PATTERN
   • Horizontal: Add replicas behind load balancer
   • Vertical: Increase container resources
   • Database: Connection pooling with Redis
   • Each service scales independently

SECURITY LAYERS:

1. Network Level
   • Reverse proxy hides internal routes
   • NetworkPolicy in Kubernetes (pod-to-pod rules)
   • Private network between services
   • TLS for external communication

2. Application Level
   • JWT for user authentication
   • Service tokens for service-to-service auth
   • RBAC for fine-grained access control
   • Permission dependency injection

3. Data Level
   • Database-level permissions
   • Encrypted secrets storage
   • Audit logging of sensitive operations
   • SQL injection prevention (ORM parameterized queries)

Q1: How does microservice architecture work behind the scenes?

A: Five core components:

   1. REVERSE PROXY (NGINX)
      - Single entry point for all clients
      - Routes requests to appropriate service based on URL path
      - Handles TLS encryption/decryption
      - Prevents client from knowing service URLs
      
   2. SERVICE DISCOVERY
      - Services find each other automatically
      - Local: Docker DNS resolution
      - Kubernetes: Built-in DNS with service names
      - Azure: DAPR sidecar handles discovery
      - GCP: Manual via environment variables + IAM
      
   3. INTER-SERVICE COMMUNICATION
      - Services call each other via HTTP
      - Authenticate with service tokens (not user tokens)
      - Example: mailsvc makes internal call to authsvc
        POST http://authsvc/internal/get-user-roles
        Authorization: Bearer service-token-xyz
      
   4. STATE MANAGEMENT
      - Each service has own database (no shared db)
      - Cache layer (Redis) for fast lookups
      - Eventual consistency for cross-service data
      - Event-driven for async updates
      
   5. ERROR HANDLING
      - Timeouts prevent hanging requests
      - Retries with backoff for transient failures
      - Circuit breakers stop cascading failures
      - Health checks detect service availability

Q2: Do I need to include a reverse proxy?

A: YES, for production. Reasons:

   FUNCTIONAL:
   • Single entry point (clients don't know service URLs)
   • Path-based routing (one URL for all services)
   • Load balancing (distribute traffic to replicas)
   
   SECURITY:
   • TLS termination (centralized encryption)
   • Hide internal routes (/internal/*)
   • Rate limiting (DDoS protection)
   • Security headers (HSTS, CSP, etc.)
   
   OPERATIONAL:
   • Service replacement (swap backend without client change)
   • Transparent scaling (add replicas without client change)
   • Centralized logging and monitoring
   • A/B testing and canary deployments
   
   PERFORMANCE:
   • Single TLS handshake (vs one per service)
   • Connection pooling
   • Caching
   • Compression

   ALTERNATIVE: Cloud Load Balancer
   Instead of NGINX, you can use:
   • Azure Load Balancer
   • GCP Cloud Load Balancing
   • AWS Application Load Balancer
   (These are managed reverse proxies)

Q3: How does this work with Azure Container Apps / GCP Cloud Run?

A: Very different approaches to service discovery:

   KUBERNETES (reference architecture):
   • Services on same cluster network
   • Call each other by DNS name: http://authsvc:8080
   • No TLS needed internally
   • Latency: 50-100ms
   
   AZURE CONTAINER APPS:
   • Each service runs as independent container
   • DAPR sidecars for service discovery
   • Automatic mTLS between services
   • Call pattern: http://authsvc (DAPR handles routing)
   • Latency: 300-600ms (DAPR overhead)
   • Cold start: 500ms
   
   GCP CLOUD RUN:
   • Each service has public HTTPS URL
   • IAM service accounts for authentication
   • No automatic discovery (manual URL management)
   • Call pattern: https://authsvc-xyz.run.app (hardcoded URL)
   • Service tokens replaced with IAM bearer tokens
   • Latency: 400-800ms (HTTPS + IAM overhead)
   • Cold start: 100-500ms

   LOCAL DEVELOPMENT:
   • Docker Compose with bridge network
   • Services on same Docker network
   • Call each other by service name
   • NGINX reverse proxy for local testing
   • No TLS internally (just HTTP)
